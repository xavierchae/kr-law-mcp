**한 일**

- 요구사항 질의응답으로 스펙 확정: Python, 로컬 stdio, 현행법령 검색·본문·조문 조회, 법률·시행령·시행규칙 전체, 마크다운 응답, uv 로컬 프로젝트, 캐싱 없음.
- 추가 요구 반영: 계획서를 `docs/PLAN.md`로, 진행 기록을 이 일지로 관리. 약칭·일부 단어로 법령명 매칭 ("생명윤리법" → 「생명윤리 및 안전에 관한 법률」).

**결정과 이유**
- 시행일 기준 `target=eflaw` + `nw=3`(현행)을 기본으로 함. "현행"은 지금 시행 중인 버전을 뜻하므로 공포일 기준(`law`)보다 정확하다.
- 조·항·호·목 조회는 본문 API에 `JO`만 넣어 한 조를 받고 항·호·목은 로컬에서 고름. `eflawjosub`은 `efYd` 필수 여부가 가이드상 모호해서 대안으로 남김.

## 2026-11-09 — 1차 구현

**한 일**
- uv 프로젝트 생성 (Python 3.12, `mcp` 2.3, httpx, rapidfuzz / dev: pytest, pytest-asyncio, respx, ruff). uv가 없어 Homebrew로 설치함.
- 모듈 구현: `models.py`, `parsing.py`, `client.py`, `aliases.py`, `resolver.py`, `formatting.py`, `server.py`.
- 도구 4개: `search_laws`, `get_law_overview`, `get_law_articles`, `get_article`.
- 테스트 80개 통과 (실제 API 호출 테스트 8개는 `-m live`로 분리). `ruff check` 통과.
- MCP stdio 클라이언트로 서버 기동, 도구 4개 노출, 도구 호출 응답까지 확인.

**결정과 이유**
- `mcp` 2.x에서 FastMCP가 `MCPServer`(`mcp.server.mcpserver`)로 바뀌어 그에 맞춤.
- `law_kind` 필터는 `knd` 코드 대신 응답의 `법령구분명`으로 로컬 필터링. 가이드에 `knd` 코드표가 없다.
- 약칭 처리를 세 단계로 나눔: 관용 약칭 정적 별칭표(`aliases.py`, 예: 근기법·산안법·중처법), 쿼리 변형 검색, 마지막으로 공식 약칭 목록 API(`lsAbrv`). `lsAbrv`는 검색어 없이 전체 목록을 반환하므로 비용이 커서 마지막에만 호출한다.
- 법령명 검색이 공백까지 정확히 비교하는 부분 일치라고 보수적으로 가정. 그래서 "개인정보보호법"처럼 띄어쓰기가 다른 입력은 앞 4글자("개인정보") 변형 검색으로 후보를 모은 뒤, 공백을 무시한 비교로 순위를 정한다.
- 해석된 법령명이 입력과 다르면 응답 첫 줄에 "법령명 해석: '생명윤리법' → 「…」"를 표시해 오매칭을 바로 알 수 있게 함.
- httpx가 INFO 로그에 요청 URL(OC 키 포함)을 남기므로 httpx 로그 수준을 WARNING으로 낮춤.

**API 확인 결과**
- `OC=test`로 호출하면 HTTP 200에 다음 JSON이 온다. 클라이언트가 이 형태를 오류로 바꾸도록 구현했다.
  ```json
  {"result": "사용자 정보 검증에 실패하였습니다.",
   "msg": "OPEN API 호출 시 사용자 검증을 위하여 정확한 서버장비의 IP주소 및 도메인주소를 등록해 주세요."}
  ```
- 즉, OC 키 외에 **호출하는 PC의 IP나 도메인을 open.law.go.kr에 등록**해야 한다.
- 실제 응답을 받지 못해 테스트 픽스처는 가이드 필드명으로 만든 합성본(`tests/fixtures/synthetic_*.json`)이다.

**남은 과제**

- [x] `LAW_OC=<키> SAVE_FIXTURES=1 uv run pytest -m live`로 실제 응답 저장 후 합성 픽스처와 구조 비교. 확인할 점은 다음과 같다.

  - `ID`만으로 본문 조회 시 `efYd` 없이 동작하는지, `JO` 지정 시 응답 형태

## 2026-11-09 — 실제 API 검증

**한 일**
- 사용자가 OC 키를 `~/.zshrc`에 설정하고 IP를 등록함. live 테스트 8개 모두 통과.
- 실제 응답을 `tests/fixtures/real_*.json`으로 저장하고, 이를 쓰는 파싱 테스트를 추가함. 단위 테스트는 86개로 늘어남.
- 실제 API로 법령명 해석과 4개 도구 출력을 점검함. 민법 전체, 민법 제312조~제312조의2, 건축법 목 단위, 생명윤리법 약칭, 근로기준법 부칙·별표, 본문검색, 종류 필터를 확인함.
- 발견한 문제 수정 (아래).

**API 확인 결과** (DEVLOG 1차 구현의 남은 과제에 대한 답)
- 응답 구조는 가이드와 합성 픽스처의 가정과 일치함. `JO`를 주면 `조문단위`가 list가 아닌 dict로 오고, `조문내용`은 문자열, 항·호·목은 list로 중첩됨. 소관부처와 법종구분은 `{"content": ..., "...코드": ...}` 형태임.
- `ID`만으로 본문 조회가 되고 `efYd`는 필요 없음.
- 법령명 검색 `query`는 **띄어쓰기를 무시**함 ("개인정보보호법" → 「개인정보 보호법」). 부분 일치라서 "민법"을 검색하면 「난민법」도 나옴.
- 법령명 검색은 **약칭에 걸리지 않음** ("생명윤리법" → 0건). 그래서 별칭표와 변형 검색, 약칭 목록 단계가 필요함.
- 시행규칙의 `법령구분명`은 "부령"이 아니라 "고용노동부령", "법무부령"처럼 부처명이 붙음.
- `lsAbrv` 약칭 목록은 2,714건, 약 2.1MB이고 호출에 약 2.6초가 걸림. 해석이 애매한 입력에서만 호출됨.
- 해석 소요 시간: 대부분 0.2~0.5초, API 1~2회 호출. 애매한 입력("보호법")만 약 3.3초.
- 검색 결과의 `법령상세링크`에 호출자의 OC 값이 그대로 들어 있음.

**결정·변경과 이유**
- OC 키가 로그에 노출되는 문제를 고침. httpx 로그 수준을 서버 시작 함수가 아니라 `client.py` import 시점에 낮춤. 다른 경로로 모듈을 쓰면 요청 URL이 INFO로 찍혔기 때문이다.
- 저장 응답의 키를 제거함. 저장 헬퍼가 `OC=...`를 `OC=test`로 치환하고, 약칭 목록은 몇 건만 남김.
- 편·장·절 제목의 줄바꿈을 한 줄로 합침. 민법 목차에서 개정 표기가 줄바꿈되어 굵은 글씨 마크다운이 깨졌다.
- 종류 우선순위가 "○○부령"을 인식하게 함 (`resolver.kind_rank`).

**남은 과제**
- [ ] Claude Code에 서버를 등록해 대화로 시나리오 수행 (등록 명령은 README 참고). 1차 구현 항목의 같은 과제와 동일.
